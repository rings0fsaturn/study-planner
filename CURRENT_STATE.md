**Deviations:**

#### Account-switch isolation: per-user DB instead of wipe

The original spec called for wiping the local EventStore when a different user signs in. During implementation we discovered a critical bug: **wiping the shared database permanently destroyed User A's data** when User B signed in, because both users shared a single IndexedDB (`StudyTracker`).

**What we built instead:** Each user gets their own Dexie database named `StudyTracker_<userId>`. When the signed-in user changes, `EventStoreProvider` closes the old DB connection and opens the new user's DB. There is no cross-account bleed, and returning users find their data intact.

**Impact on acceptance criteria:** The criterion "Signing out and signing in as a different user wipes the local EventStore" still passes — the previous user's sessions are not visible to the new user. The mechanism is isolation, not deletion.

**Implementation notes:** AuthProvider was cleaned of all wipe logic, localStorage tracking, and EventStore imports. EventStoreRouter in App.tsx reads user from AuthContext and passes userId to EventStoreProvider — zero coupling between auth and events layers.

## 4. Conventions established

Patterns the next slice should follow. Derived from implementation notes across done issues plus inspection of the code that landed.

- **Deep modules with constructor DI.** AuthGate and EventStore both accept their external dependencies (Supabase client, Dexie DB) via constructor — enables hand-written fakes in tests. See `apps/app/src/auth/AuthGate.ts:3` and `apps/app/src/events/EventStore.ts:1`.
- **Hand-written test fakes, not generated mocks.** The fake Supabase client in `AuthGate.test.ts` is a plain object implementing the needed surface. No `jest.mock` or MSW.
- **Pure function modules for business logic.** ProgressEngine has no I/O — it takes events as input and returns derivations. See `apps/app/src/events/ProgressEngine.ts`.
- **React context providers for DI wiring.** AuthProvider wraps the app with Supabase client; EventStoreProvider wraps children with a per-user Dexie DB. Both track `loading`/`ready` state so consumers never render before dependencies are available.
- **Per-user storage isolation.** IndexedDB databases are named `StudyTracker_<userId>` — never shared across accounts. This pattern applies to any future local-storage module.
- **CSS via design-tokens workspace package.** All styling uses `@study-tracker/design-tokens` imports (`global.css`, `tokens.css`, `components.css`). No CSS-in-JS, no Tailwind. Primitive component classes (`.btn`, `.card`, `.field`) are used alongside semantic type roles (`.t-display-1`, `.t-body`).
- **Vite `base: '/study/'` and `envPrefix: ['VITE_', 'SUPABASE_']`.** All app URLs live under `/study/`. Supabase env vars use bare `SUPABASE_` prefix (not `VITE_`), explicitly allowed via `envPrefix`.
- **Route pages are top-level in `src/pages/`.** Each route gets its own file (SignIn.tsx, Home.tsx, Log.tsx). Components shared across routes live in `src/components/`.
- **Auth init has a 500ms timeout.** AuthProvider uses `setTimeout` to flip `loading` to false after 500ms if Supabase hasn't responded — prevents React from hanging on slow auth init. See `.opencode/rules/auth-init-timeout.md`.
- **TypeScript strict throughout.** No `any` escape hatches in module code. `vite-env.d.ts` declares env var types explicitly.
