# Onboarding with manual-only materials (Slice 4)

**Slug:** `004-onboarding-with-manual-materials`
**Date written:** 2026-04-29
**Author:** Claude + user
**Plan status:** Draft
**Upstream:** [`issues/004-onboarding-with-manual-materials.md`](../issues/004-onboarding-with-manual-materials.md)

## TL;DR

A new user signs in for the first time and is walked through a 4-step onboarding flow: deadline → weekly hours + study days → materials entry with live plan preview → confirmation. The plan preview is generated by `@study-tracker/progress-engine` (the RoadmapEngine algorithm from slice 4a). On desktop (≥1024px), step 3 uses a two-column layout with the materials form on the left and a live-updating preview on the right; on mobile, the preview is a separate sub-screen. Committing emits `MaterialAdded` × N, `RoadmapCreated`, and `OnboardingCompleted` events via the existing SyncEngine. After commit, the Home screen shows projected finish and an "Up next" card derived from the committed roadmap.

## Context & background

This is Slice 4 of the Study Tracker web app, building on:
- **Slice 2** — Event sync infrastructure (`SyncEngine`, `SyncProvider`, `useSync().logEvent()`)
- **Slice 3** — Auth gate, EventStore with per-user Dexie DBs, Home and Log pages
- **Slice 4a** — `RoadmapEngine` algorithm (`packages/progress-engine/`), which generates slot-based study plans

The onboarding flow bridges what the user tells us about their schedule (deadline, hours, study days, materials) to a concrete week-by-week plan. RoadmapEngine handles the heavy algorithmic lifting. This slice handles everything around it: form UX, preview rendering, tie resolution, capacity prompts, commit sequencing, and post-commit Home integration.

**Design reference:** `design/screens.html` — Section B (mobile onboarding) and sections K3–K5 (desktop onboarding). Every component uses existing Marginalia design-system CSS classes from `packages/design-tokens/`.

**Support docs:**

- `design/algo/ROADMAP_ENGINE_GUIDE.md` — RoadmapEngine integration guide
- `design/screens.html` — visual reference for all screens

## Decisions log

### D-01: Onboarding draft state lives in OnboardingProvider React context + Dexie `onboardingDraft` table

**Status:** ✅ Agreed

**Context:** The onboarding flow spans 4 steps. In-progress data (deadline, hours, materials, preview edits) must survive forward/back navigation between steps and survive tab refresh. It must NOT sync to the cloud (drafts, not committed events).

**Decision:** A new `OnboardingProvider` React context holds active state via `useReducer`. On change, it persists to a dedicated `onboardingDraft` table in the per-user Dexie instance (schema v3). On mount, it restores any existing draft row. On commit, the draft is cleared.

**Rationale:** URL params would leak long material data. EventStore would pollute the event log with drafts. A dedicated Dexie table gives the same per-user isolation guarantees with no extra infrastructure.

**Alternatives considered:**
- URL params → rejected: URL length limits, complex data shapes
- EventStore `'OnboardingProgress'` events → rejected: mixes draft/committed data, cleanup complexity
- `sessionStorage` only → rejected: doesn't survive tab crash on iOS Safari

**User pushback / disagreement:** User asked "We need to save the progress to eventStore or IndexedDB" — resolved to Dexie table.

**Reversibility:** Moderate. Switching to a different persistence backend requires migrating the draft table shape.

### D-02: OnboardingGate checks EventStore for `OnboardingCompleted` event

**Status:** ✅ Agreed

**Context:** First-time users must see onboarding; returning users (with `OnboardingCompleted` in their event log) must skip it. This check needs to work on fresh devices too (after SyncEngine restores from cloud).

**Decision:** `OnboardingGate` wraps the onboarding route group. On mount, it queries EventStore (via `useLiveQuery`) for any `kind === 'OnboardingCompleted'` event. If found → redirect to `/home`. If not → render children.

**Rationale:** The EventStore is the single source of truth. SyncEngine restores `OnboardingCompleted` on fresh devices, so the skip works automatically post-restore. No secondary flag in auth metadata needed.

**Alternatives considered:**
- `user.user_metadata.has_onboarded` boolean → rejected: second source of truth, desync risk
- `localStorage` key → rejected: doesn't survive cross-device sign-in

**User pushback / disagreement:** None.

**Reversibility:** Easy. Gate is a thin wrapper component — replace or remove without affecting the flow itself.

### D-03: Skip-ahead guard based on context data presence

**Status:** ✅ Agreed

**Context:** If a user bookmarks `/onboarding/3` and returns later without step 1-2 data, they must be redirected to the earliest incomplete step.

**Decision:** Each step component imports `useOnboarding()` and checks derived completion flags: `step1Complete = deadline !== null`, `step2Complete = selectedStudyDays.length > 0 && weekdayHours + weekendHours === weeklyHours`. A `CheckpointGate` component wraps each step's content and `<Navigate>`s to the earliest incomplete step if the current step's prereqs aren't met. No route-guard component — inline in each step.

**Rationale:** Simple derived checks on the same context state. Self-correcting on back-navigation. Handles bookmark restoration without server round-trip.

**Alternatives considered:**
- `onBeforeRouteChange` hook → rejected: overkill, context state already available
- URL-based guard (check referrer) → rejected: brittle, breaks on bookmark

**User pushback / disagreement:** None.

**Reversibility:** Easy. Inline checks can be moved to a shared guard if needed.

### D-04: Nested route group for onboarding with `<Outlet />` layout

**Status:** ✅ Agreed

**Context:** The onboarding flow has 4 steps at `/onboarding/1` through `/onboarding/4`, plus a mobile-only sub-route `/onboarding/3/preview`. Each step should be independently bookmarkable.

**Decision:** A nested `<Route path="/onboarding">` group with `<OnboardingLayout>` (renders `<Outlet />` + step dots + shared chrome). Routes: `/onboarding` redirects to `/onboarding/1`. Steps map to `/onboarding/1` through `/onboarding/4`. Mobile-only `/onboarding/3/preview` as a child of step 3 — on desktop it's unreachable (step 3 renders the preview inline).

**Rationale:** Nested routes mean `OnboardingGate` and `OnboardingProvider` mount once, not on every step transition. Shared chrome stays persistent. React Router handles forward/back naturally.

**Alternatives considered:**
- Single `/onboarding` route with step index in context → rejected: issue requires bookmarkable per-step URLs

**User pushback / disagreement:** User required mobile preview as separate screen (matching `design/screens.html` step 4 mobile), desktop fused. Option A (4 dots, sub-route on mobile) accepted.

**Reversibility:** Moderate. Route structure is in App.tsx; changing it touches all step components.

### D-05: Per-user Dexie schema v3 adds `onboardingDraft` table

**Status:** ✅ Agreed

**Context:** The `EventStoreProvider` currently creates Dexie schemas v1 (events) + v2 (events, sync_queue, sync_meta). The onboarding draft needs its own table.

**Decision:** Add `db.version(3).stores({ onboardingDraft: 'id' })` to `createEventStore()`. The table has a single row with `id: 1`. Accessed via `eventStore.table('onboardingDraft')`. No sync — the table is excluded from the EventStore's public methods (only used via raw table access).

**Rationale:** Dexie auto-migrates existing databases — v2 → v3 adds the table without data loss. Same per-user DB = same isolation. Raw table access bypasses the EventStore public API which would otherwise log these as events.

**Alternatives considered:**
- Separate Dexie instance → rejected: double connection management, no isolation benefit
- `localStorage` for draft → rejected: per-user isolation not guaranteed

**User pushback / disagreement:** None.

**Reversibility:** Hard. Dexie version migration is forward-only per Dexie's design. Once deployed, v3 cannot be removed without breaking existing user databases.

### D-06: `date-fns` v4 for all date math

**Status:** ✅ Agreed

**Context:** Onboarding needs deadline→weeks calculation, chip offsets (addDays, addWeeks, addMonths), date formatting for display, and "today" computation. The RoadmapEngine rolls its own inline `addDaysISO` for UTC math, but the UI has broader date needs.

**Decision:** Add `date-fns` v4 as a dependency to `apps/app/package.json`. Use `differenceInCalendarDays`, `addDays`, `addWeeks`, `addMonths`, `format`, `isBefore`, `startOfToday`.

**Rationale:** Tree-shakeable (~3KB gzipped). Handles DST transitions and month boundaries correctly. Already likely to be needed for weekly progress view (slice 11). Vanilla Date math risks DST bugs in `daysBetween` calculations.

**Alternatives considered:**
- Vanilla `Date` math → rejected: DST edge-case risk, more verbose
- `dayjs` → rejected: no tree-shaking, larger bundle
- `luxon` → rejected: heavier, overengineered for this use case

**User pushback / disagreement:** None. User agreed: "Yes agreed."

**Reversibility:** Easy. Swap library by updating imports and call sites.

### D-07: ROLE↔LABEL mapping lives in `progress-engine` package

**Status:** ✅ Agreed

**Context:** The UI uses plain-English labels ("Main reading", "Foundations", "Practice") but the engine uses `'anchor'`, `'foundation'`, `'practice'`. The mapping is needed by the dropdown component, the preview renderer, and any future material-edit dialog.

**Decision:** Two exported consts in `packages/progress-engine/src/constants.ts`:
```ts
export const ROLE_TO_LABEL: Record<MaterialRole, string> = { anchor: 'Main reading', foundation: 'Foundations', practice: 'Practice' }
export const LABEL_TO_ROLE: Record<string, MaterialRole> = { 'Main reading': 'anchor', 'Foundations': 'foundation', 'Practice': 'practice' }
```

**Rationale:** The mapping is part of the type taxonomy — placing it in the engine package means all consumers get consistent labels. The dropdown becomes a thin UI wrapper.

**Alternatives considered:**
- Co-located with dropdown component → rejected: duplication across preview/home/settings
- Only in the app, not the engine package → rejected: engine already owns `MaterialRole` type

**User pushback / disagreement:** None. "Yes makes sense."

**Reversibility:** Easy. Constants are pure data.

### D-08: `inferRole()` fires reactively on every change to title + duration

**Status:** ✅ Agreed

**Context:** The Type dropdown should pre-select based on the material title, but `inferRole()` needs both `title` and `estimatedMinutes` (the "largest seen so far" rule). If only one field is filled, the inference isn't meaningful.

**Decision:** Fire `inferRole()` whenever both `title` is non-empty AND `estimatedMinutes > 0`. Pass all previously added materials as `existingMaterials` (in `additionOrder`, excluding the current row). Once the user explicitly overrides the dropdown, set `userOverrodeType: true` on the material row and stop further inference for that row. Fires on keystroke, not just blur.

**Rationale:** Immediate feedback matches the "preview re-renders within 200ms" requirement. The override flag prevents the inference from fighting the user's explicit choice.

**Alternatives considered:**
- Fire only on blur → rejected: misses the case where user fills duration before title
- Fire on title-only → rejected: the "largest seen" rule produces wrong results without duration

**User pushback / disagreement:** None. "Agreed."

**Reversibility:** Easy. Inference function signature is stable.

### D-09: `generateRoadmap()` debounced at 150ms

**Status:** ✅ Agreed

**Context:** The issue requires the preview to "re-render within 200ms of any input change." Calling `generateRoadmap()` on every keystroke during title typing is wasteful.

**Decision:** Debounce the `generateRoadmap()` call at 150ms. Form fields update immediately (React state). Only the preview panel re-renders on the debounced engine output. Use React's `useDeferredValue` or a `useDebounce` hook (150ms timer).

**Rationale:** 150ms stays within the 200ms requirement. Typing "Designing Data-Intensive Applications" would call the engine ~30 times without debounce; with it, fires once after the user pauses.

**Alternatives considered:**
- Benchmark first, only debounce if needed → rejected: user explicitly chose debounce.
- No debounce → rejected by user.

**User pushback / disagreement:** None. "debounce."

**Reversibility:** Easy. Remove the hook and call directly.

**Status:** ✅ Agreed

**Context:** `design/screens.html` shows separate mobile screens for materials (step 3) and preview (step 4 of 5 in the design file), but fuses them on desktop. The issue spec defines 4 steps, not 5.

On desktop (≥1024px), `/onboarding/3` renders both columns side-by-side; `/onboarding/3/preview` does not exist (unreachable because desktop users see preview inline). Step dots always show 4 dots.

**Alternatives considered:**

- 5 separate steps → rejected by user: accepted Option A (4 dots)

**User pushback / disagreement:** "No in mobile i want it in a new screen as per `<!-- ============ STEP 4 · PREVIEW · MOBILE ============ -->` ... And in Desktop i want it fused 2 column"

### D-11: Material IDs are `crypto.randomUUID()` generated at creation time

**Status:** ✅ Agreed

**Context:** Materials are in-memory drafts until commit, but `MaterialAdded` events need stable UUIDs, and `RoadmapCreated` must reference them by `materialId`. IDs must exist before commit.

**Decision:** Generate a UUID via `crypto.randomUUID()` when a material is first added on step 3. The UUID lives in `material.id` in the draft state. On commit, the same UUID flows into `MaterialAdded.payload.materialId` and `RoadmapCreated` slot `materialId` references.

**Rationale:** `crypto.randomUUID()` is available in all modern browsers (Chrome 92+, Firefox 95+, Safari 15.4+). UUIDs are collision-safe without coordination. Generated at creation time, stable across all preview re-renders and edits.

**Alternatives considered:**
- Sequential counters (1, 2, 3) → rejected: collisions across users if sync merges? No (per-user tables), but less clean
- Server-assigned IDs → rejected: no round-trip before commit

**User pushback / disagreement:** None. "Agreed."

**Reversibility:** Easy. ID generation is one line.

### D-12: Commit emits events sequentially via `useSync().logEvent()`, not atomically batched

**Status:** ✅ Agreed

**Context:** The commit sequence is `MaterialAdded` × N → `RoadmapCreated` → `OnboardingCompleted`. Each `logEvent()` call is synchronous to local Dexie and enqueued to sync. No transaction wrapping available at the `SyncEngine` level.

**Decision:** Emit sequentially. Each `logEvent()` call completes (IndexedDB write confirmed) before the next begins. Browser crash after N of M events means partial commit — acceptable v1 tradeoff. Network sync failure is handled by the existing retry queue (exponential backoff in SyncEngine).

**Rationale:** Batching would require architectural changes to `SyncEngine.logEvent()` (accept array, atomic append). The existing sequential approach with local durability is sufficient for v1 — partial-onboard scenarios are vanishingly rare and the retry handles the 99% case.

**Alternatives considered:**
- Batch events via `eventStore.bulkAppend()` directly → rejected: bypasses SyncEngine, events wouldn't sync
- Modify `SyncEngine` for atomic multi-event → rejected: scope creep for this slice

**User pushback / disagreement:** None.

**Reversibility:** Moderate. Would require SyncEngine API change.

### D-13: Home reads roadmap from EventStore directly via `useLiveQuery()`

**Status:** ✅ Agreed

**Context:** After onboarding, Home must show projected finish date and "Up next" slot. The `RoadmapCreated` event payload contains the full slot grid.

**Decision:** Home already uses `useLiveQuery(() => eventStore.getAll())`. Extend it to find the latest `RoadmapCreated` or `RoadmapReplanned` event, extract the last non-rest-day slot for "projected finish", and the first upcoming non-rest-day slot (date ≥ today) for "Up next". New pure helpers in `ProgressEngine`: `getProjectedFinish(roadmap: RoadmapOutput)` and `getUpNextSlot(roadmap: RoadmapOutput, today: string)`. New devices automatically see roadmap data after SyncEngine restores from cloud.

**Rationale:** No new event emission needed. Home already reads events reactively. Pure helpers keep logic testable. SyncEngine handles the fresh-device case (cloud restore → events replayed → `useLiveQuery` fires).

**Alternatives considered:**
- Emit `ProjectedFinish` as a separate event → rejected: derived data shouldn't be synced
- Store computed values in a separate IndexedDB table → rejected: adds a secondary cache to maintain

**User pushback / disagreement:** User confirmed concern: "For a new device lets say mobile when they view homescreen how will they see Finish and up next data?" — answered: SyncEngine restores `RoadmapCreated` from cloud, `useLiveQuery` reactively picks it up.

**Reversibility:** Easy. The helpers are pure functions.

### D-16: Event payload types defined in `sync/types.ts`

**Status:** ✅ Agreed

**Context:** `MaterialAdded`, `RoadmapCreated`, and `OnboardingCompleted` events need consistent payload shapes. The existing `SyncEngine.logEvent()` accepts `{ kind: string, payload: Record<string, unknown> }` — untyped.

## Architecture overview

```
App.tsx (BrowserRouter basename="/study")
  └─ AuthProvider
       └─ EventStoreRouter (creates per-user Dexie)
            └─ SyncRouter (wraps with SyncProvider when user+store ready)
                 └─ Routes
                      ├─ /home (ProtectedRoute → Home)
                      ├─ /log (ProtectedRoute → Log)
                      └─ /onboarding (OnboardingGate → OnboardingProvider → OnboardingLayout → Outlet)
                           ├─ / (redirect → /onboarding/1)
                           ├─ /1 (Step1Deadline)
                           ├─ /2 (Step2Hours)
                           ├─ /3 (Step3Materials)       ← desktop: two-column, mobile: form only
                           │    └─ /preview (Step3Preview)  ← mobile only
                           └─ /4 (Step4Confirm)
```

**Data flow during onboarding:**

```
Step1 form → dispatch → OnboardingProvider context state → persist to Dexie onboardingDraft
Step2 form → dispatch → context → persist
Step3 materials → dispatch → context → persist
                  ↓                                   ↓
           inferRole(title, mins, existing)    generateRoadmap(input) [debounced 150ms]
                  ↓                                   ↓
           Type dropdown default               RoadmapOutput (weeks, warnings, capacityCheck)
                                               → preview renders schedule-card
                                               → multi-candidate slots render as chips
                                               → tie resolution updates draft sessionTitle
                                               → capacity warnings block/enable commit

Commit (step 3):
  for each material: useSync().logEvent('MaterialAdded', { materialId, title, ... })
  useSync().logEvent('RoadmapCreated', { startDate, weeks, deadline, slots, ... })
  useSync().logEvent('OnboardingCompleted', {})
  eventStore.table('onboardingDraft').clear()
  navigate('/onboarding/4')
```

   ```tsx
   import { createContext, useContext, useReducer, useEffect, type ReactNode } from 'react'
   import { useEventStore } from '../events/useEventStore'
   import type { DayOfWeek, MaterialRole } from '@study-tracker/progress-engine'

   export interface OnboardingMaterial {
     id: string
     title: string
     estimatedDuration: number
     role: MaterialRole
     url?: string
     additionOrder: number
     userOverrodeType: boolean
   }

   export interface OnboardingSlotEdit {
     weekIndex: number
     dayOfWeek: string
     materialId: string | null  // null = user chose rest day
     sessionTitle: string | null
     plannedMinutes: number
   }

   export interface OnboardingState {
     deadline: string | null           // ISO date YYYY-MM-DD
     purpose: string                   // "What are you preparing for?"
     weeklyHours: number               // total weekly hours
     weekdayHours: number              // subset for weekdays
     weekendHours: number              // subset for weekends
     selectedStudyDays: DayOfWeek[]    // checked Mon–Sun
     materials: OnboardingMaterial[]
     previewEdits: OnboardingSlotEdit[]   // tie resolutions + inline renames
     stepReached: number               // highest step visited (for checkpoint)
   }

   const INITIAL_STATE: OnboardingState = {
     deadline: null,
     purpose: '',
     weeklyHours: 0,
     weekdayHours: 0,
     weekendHours: 0,
     selectedStudyDays: [],
     materials: [],
     previewEdits: [],
     stepReached: 1,
   }

   type OnboardingAction =
     | { type: 'SET_DEADLINE'; deadline: string | null; purpose?: string }
     | { type: 'SET_HOURS'; weeklyHours: number; weekdayHours: number; weekendHours: number; selectedStudyDays: DayOfWeek[] }
     | { type: 'ADD_MATERIAL'; material: OnboardingMaterial }
     | { type: 'UPDATE_MATERIAL'; id: string; updates: Partial<OnboardingMaterial> }
     | { type: 'REMOVE_MATERIAL'; id: string }
     | { type: 'SET_PREVIEW_EDITS'; edits: OnboardingSlotEdit[] }
     | { type: 'SET_STEP_REACHED'; step: number }
     | { type: 'RESTORE'; state: OnboardingState }
     | { type: 'RESET' }

   function onboardingReducer(state: OnboardingState, action: OnboardingAction): OnboardingState {
     switch (action.type) {
       case 'SET_DEADLINE':
         return { ...state, deadline: action.deadline, purpose: action.purpose ?? state.purpose, stepReached: Math.max(state.stepReached, 1) }
       case 'SET_HOURS':
         return { ...state, weeklyHours: action.weeklyHours, weekdayHours: action.weekdayHours, weekendHours: action.weekendHours, selectedStudyDays: action.selectedStudyDays, stepReached: Math.max(state.stepReached, 2) }
       case 'ADD_MATERIAL':
         return { ...state, materials: [...state.materials, action.material], stepReached: Math.max(state.stepReached, 3) }
       case 'UPDATE_MATERIAL':
         return { ...state, materials: state.materials.map(m => m.id === action.id ? { ...m, ...action.updates } : m) }
       case 'REMOVE_MATERIAL':
         return { ...state, materials: state.materials.filter(m => m.id !== action.id) }
       case 'SET_PREVIEW_EDITS':
         return { ...state, previewEdits: action.edits }
       case 'SET_STEP_REACHED':
         return { ...state, stepReached: Math.max(state.stepReached, action.step) }
       case 'RESTORE':
         return { ...state, ...action.state }
       case 'RESET':
         return INITIAL_STATE
       default:
         return state
     }
   }

   interface OnboardingContextValue {
     state: OnboardingState
     dispatch: React.Dispatch<OnboardingAction>
     ready: boolean
   }

   const OnboardingContext = createContext<OnboardingContextValue | null>(null)

   export function OnboardingProvider({ children }: { children: ReactNode }) {
     const eventStore = useEventStore()
     const [state, dispatch] = useReducer(onboardingReducer, INITIAL_STATE)
     const [ready, setReady] = useState(false)

     // Restore draft from Dexie on mount
     useEffect(() => {
       const table = eventStore.table('onboardingDraft')
       table.get(1).then((row: { state: OnboardingState } | undefined) => {
         if (row?.state) {
           dispatch({ type: 'RESTORE', state: row.state })
         }
         setReady(true)
       }).catch(() => {
         setReady(true)
       })
     }, [eventStore])

     // Persist draft to Dexie on every state change (after initial restore)
     const isFirstRender = useRef(true)
     useEffect(() => {
       if (isFirstRender.current) {
         isFirstRender.current = false
         return
       }
       const table = eventStore.table('onboardingDraft')
       table.put({ id: 1, state }).catch(() => {})
     }, [state, eventStore])

     return (
       <OnboardingContext.Provider value={{ state, dispatch, ready }}>
         {children}
       </OnboardingContext.Provider>
     )
   }

   export function useOnboarding() {
     const ctx = useContext(OnboardingContext)
     if (!ctx) throw new Error('useOnboarding must be used within OnboardingProvider')
     return ctx
   }
   ```

   ```tsx
   import { type ReactNode } from 'react'
   import { Navigate } from 'react-router-dom'
   import { useOnboarding } from './OnboardingProvider'

   interface CheckpointGateProps {
     step: number
     children: ReactNode
   }

   const STEP_PREREQS: Record<number, (state: ReturnType<typeof useOnboarding>['state']) => boolean> = {
     1: () => true,
     2: (s) => s.deadline !== null,
     3: (s) => s.selectedStudyDays.length > 0 && s.weeklyHours > 0
         && s.weekdayHours + s.weekendHours === s.weeklyHours,
     4: (s) => s.materials.length >= 1,
   }

   export function CheckpointGate({ step, children }: CheckpointGateProps) {
     const { state } = useOnboarding()

     const earliestIncomplete = ((): number => {
       for (let s = 1; s < step; s++) {
         const check = STEP_PREREQS[s]
         if (!check(state)) return s
       }
       return -1
     })()

     if (earliestIncomplete > 0) {
       return <Navigate to={`/onboarding/${earliestIncomplete}`} replace />
     }

     return <>{children}</>
   }
   ```

   ```tsx
   import { useEffect } from 'react'
   import { inferRole, ROLE_TO_LABEL, LABEL_TO_ROLE } from '@study-tracker/progress-engine'
   import type { OnboardingMaterial } from '../OnboardingProvider'

   const ROLE_LABEL_OPTIONS: string[] = ['Main reading', 'Foundations', 'Practice']

   interface MaterialRowProps {
     material: OnboardingMaterial
     existingMaterials: OnboardingMaterial[]
     onUpdate: (updates: Partial<OnboardingMaterial>) => void
     onRemove: () => void
   }

   export function MaterialRow({ material, existingMaterials, onUpdate, onRemove }: MaterialRowProps) {
     useEffect(() => {
       if (material.userOverrodeType) return
       if (!material.title || material.estimatedDuration <= 0) return
       const inferred = inferRole(
         material.title,
         material.estimatedDuration,
         existingMaterials.filter(m => m.id !== material.id && m.estimatedDuration > 0),
       )
       if (inferred !== material.role) {
         onUpdate({ role: inferred })
       }
     }, [material.title, material.estimatedDuration])

     const handleRoleChange = (label: string) => {
       const role = LABEL_TO_ROLE[label]
       if (role) onUpdate({ role, userOverrodeType: true })
     }

     return (
       <div className="material-row">
         <div className="material-icon bk">BK</div>
         <div className="material-body">
           <div style={{ display: 'flex', flexDirection: 'column', gap: '10px' }}>
             <input className="field" type="text" placeholder="Material title"
               value={material.title}
               onChange={e => onUpdate({ title: e.target.value })} />
             <div style={{ display: 'flex', gap: '8px' }}>
               <div className="field-with-suffix" style={{ flex: 1 }}>
                 <input className="field" type="number" min={1} placeholder="Min"
                   value={material.estimatedDuration || ''}
                   onChange={e => onUpdate({ estimatedDuration: Number(e.target.value) })} />
                 <span className="field-with-suffix-text">min</span>
               </div>
               <select className="field" style={{ flex: 1 }}
                 value={ROLE_TO_LABEL[material.role]}
                 onChange={e => handleRoleChange(e.target.value)}>
                 {ROLE_LABEL_OPTIONS.map(l => <option key={l} value={l}>{l}</option>)}
               </select>
             </div>
             <input className="field" type="url" placeholder="URL (optional)"
               value={material.url ?? ''}
               onChange={e => onUpdate({ url: e.target.value || undefined })} />
           </div>
           {material.estimatedDuration > 0 && material.title && (
             <div className="material-meta" style={{ marginTop: '6px' }}>
               ~{material.estimatedDuration}min · {ROLE_TO_LABEL[material.role]}
             </div>
           )}
         </div>
         <button className="material-row-action" onClick={onRemove} title="Remove material">
           <svg className="icon icon-sm" viewBox="0 0 24 24">

   }
   ```
