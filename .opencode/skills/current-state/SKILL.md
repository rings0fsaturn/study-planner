# current-state

Generate `CURRENT_STATE.md` at the repo root: a deterministic, regenerated-from-scratch snapshot of project progress, derived from the PRD, the issue files, and git history on `main`.

The doc exists for one reason: when an agent (or a human) starts work on a new issue, they should be able to read this single file and know **what already exists, where it lives, what house style to follow, and what landmines to avoid** — without having to re-read the codebase.

## Project conventions this skill assumes

This skill is built for projects that follow a PRD → vertical-slice issues → feature-branch workflow. Specifically:

- **PRD:** a single Markdown file matching `**/PRD-*.md`.
- **Issue files:** Markdown files with a numeric prefix like `001a-...md`, `002-...md`, `017-...md`. The numeric prefix may include a letter suffix (`1a` and `1b` are distinct slices). Each issue file contains an acceptance-criteria section with checkboxes (`- [ ]` / `- [x]`).
- **Done detection:** an issue is **done** when every acceptance-criteria checkbox in its file is `- [x]`. Some checked, some not → in progress. None checked → not started.
- **Branches:** issue work happens on branches named `feature/issue-XX` where `XX` is the full issue ID including any letter suffix (e.g. `feature/issue-001a`, `feature/issue-002`). Branches are merged to `main` and deleted.
- **Optional `## Deviations` section** in the issue file captures spec deviations the user wrote up by hand.
- **Optional `## Implementation notes` section** captures useful "how it was actually built" context.

If the project clearly doesn't follow these conventions (e.g. integration branch isn't `main`, or no PRD exists), pause and ask the user before proceeding.

## Output

Write `CURRENT_STATE.md` to the repo root. Before overwriting, copy any existing `CURRENT_STATE.md` to `CURRENT_STATE.prev.md` so the user can diff what changed.

The file is **fully regenerated on every run**. Source of truth is the PRD + issue files + git — never the prior `CURRENT_STATE.md`. If the user has hand-edited it, those edits will be lost. Surface this back to them and tell them to put the note in the relevant issue file's `## Deviations` or `## Implementation notes` section instead.

## CURRENT_STATE.md template

Use this exact structure:

```markdown
# Current State

> ⚠️ Generated by the `current-state` skill. Do not edit by hand. Source of truth is the PRD, issue files, and git history on `main`.
>
> Last updated: <YYYY-MM-DD>
> PRD: <relative path>

## 1. Status snapshot

| ID   | Title                | Status                 | Merge commit |
|------|----------------------|------------------------|--------------|
| 001a | Deploy tracer + ...  | ✅ Done                | `abc1234`    |
| 001b | Email/password ...   | 🟡 In progress (4/7)  | —            |
| 002  | Log past session ... | ⬜ Not started         | —            |

Totals: N done · M in progress · K not started.

## 2. Architecture map

Where things live in the current codebase. Each entry cites the issue that introduced it. An agent on a new issue should scan this first.

- `app/` — Next.js app router root (issue 001a)
- `lib/auth/` — Supabase auth wrappers and session helpers (issue 001b)
- `lib/sync/` — Event sync layer with offline queue (issue 003)
- ... (one bullet per significant top-level directory or module)

## 3. Per-issue ledger

For each completed issue, in numeric order.

### Issue 001a — <title>

**What shipped:** <2–3 line summary derived from the issue's "What to build" plus its acceptance criteria.>

**Files added/modified:**
- `path/to/file1.ts`
- `path/to/file2.tsx`
- ... (cap at ~15; if more, append "and N more — see commit `<sha>`")

**Deviations:** <verbatim from issue's `## Deviations` section, or "None recorded">

**Implementation notes:** <verbatim from issue's `## Implementation notes` section, omit this line if the section is absent>

### Issue 001b — <title>

...

## 4. Conventions established

Patterns the next slice should follow. Derived from implementation notes across done issues plus inspection of the code that landed.

- <e.g. "All API routes return `Result<T, AppError>` — see `lib/result.ts` (issue 001b)">
- <e.g. "Component files use named exports, not default exports">
- ...

If nothing has emerged yet, write "No conventions captured yet — too early."

## 5. Open threads

Known gaps, drift, deferred decisions. Includes:

- **Drift between issue files and code:** issues marked done by checkboxes but with no commits found on `main`, or with files listed in commits that no longer exist in `HEAD`.
- **Deferred from the PRD:** items the PRD explicitly calls "deferred", "out of scope", or "v2".
- **Unresolved decisions:** anything captured in deviation notes that flagged a follow-up.
```

## Workflow

Run these steps in order. Stop and ask the user if any ambiguity surfaces — never silently pick.

### Step 1. Locate the PRD and issue files

Glob both, excluding common junk paths:

```bash
find . -name "PRD-*.md" \
  -not -path "*/node_modules/*" \
  -not -path "*/.git/*" \
  -not -path "*/dist/*" \
  -not -path "*/.next/*" \
  -not -path "*/build/*" \
  -not -path "*/.skills/*"
```

For issue files, glob for filenames matching `[0-9]*.md` (a numeric prefix). Common patterns: `001a-foo.md`, `02-bar.md`, `017-baz.md`.

```bash
find . -name "[0-9]*.md" \
  -not -path "*/node_modules/*" \
  -not -path "*/.git/*" \
  -not -path "*/dist/*" \
  -not -path "*/.next/*" \
  -not -path "*/build/*" \
  -not -path "*/.skills/*" \
  | sort
```

Sort by filename so `001a` precedes `001b` precedes `002`.

**Pause if:**
- 0 PRD files match (ask the user where the PRD lives or whether to skip the PRD reference)
- 2+ PRD files match (ask which one to treat as canonical)
- 0 issue files match (ask whether the project uses a different naming convention)

### Step 2. Classify each issue by checkbox state

For each issue file, count occurrences of `- [ ]` (unchecked) and `- [x]` / `- [X]` (checked). Only count lines under the acceptance-criteria section if there's a clear `## Acceptance criteria` heading; otherwise count across the whole file.

- All boxes checked, ≥1 box total → **done**
- Some checked, some not → **in progress** (record `<checked>/<total>`)
- None checked → **not started**
- Zero boxes total → flag in section 5 ("issue file has no acceptance criteria — cannot infer status")

Extract the issue ID from the filename's numeric prefix, including any letter suffix (e.g. `001a-deploy-tracer-and-design-system.md` → ID `001a`).

Extract the title from the issue file's frontmatter `title:` field if present, otherwise from the first `# ` heading, otherwise from the filename.

### Step 3. Find git commits for done issues

For each done issue with ID `XX`, run a three-tier lookup against `main`. Take the first tier that returns at least one match.

```bash
# Tier 1: --no-ff merge commits (default GitHub "Create a merge commit")
git log main --merges --grep="feature/issue-XX" --format="%H %s" | head -5

# Tier 2: any commit (catches squash-merge with the branch name in the message)
git log main --grep="feature/issue-XX" --format="%H %s" | head -5

# Tier 3: loose grep (catches messages that drop the "feature/" prefix)
git log main --grep="issue-XX" --format="%H %s" | head -5
```

Substitute `XX` with the full issue ID including letter suffix (e.g. `feature/issue-001a` not `feature/issue-001`).

**Resolution rules:**
- Exactly one match across the first non-empty tier → use it.
- Multiple matches in the first non-empty tier → take the most recent and note ambiguity in the per-issue ledger entry ("multiple commits matched, using `<sha>`").
- All three tiers empty → record the issue in section 5 as "completed per issue file but no commits found on main." Don't fail the run; the issue still appears in the ledger but with `Files added/modified: (none found)`.

**If `main` doesn't exist:** pause and ask the user the integration branch name (`master`, `develop`, etc.). Use whatever they say.

### Step 4. Get changed files for each merged issue

For the resolved commit `<sha>`:

```bash
# For merge commits:
git log -m -1 --name-only --diff-filter=AM --format="" <sha>

# For non-merge (squash) commits:
git show --name-only --diff-filter=AM --format="" <sha>
```

Try the merge form first; if it returns nothing, fall back to the second form.

`--diff-filter=AM` keeps only Added and Modified files, excluding deletions — important so a file deleted in a later issue doesn't pollute an earlier issue's ledger entry.

**Cross-check against `HEAD`:** for each path returned, check whether it still exists. If not, drop it from the ledger but record it in section 5 if it seems significant (e.g. a top-level module).

Cap the displayed file list per issue at ~15. If more, append `and N more — see commit <sha>`.

### Step 5. Build the architecture map

Take the union of all changed files from all done issues, dedupe, filter to files still present in `HEAD`. Group by top-level directory (`app/`, `lib/`, `components/`, etc.) or by meaningful sub-directory where useful (`lib/auth/`, `lib/sync/`).

For each group, attribute it to the **earliest** done issue that touched any file in it. Then `view` the directory listing and the most-likely entry-point file (e.g. `index.ts`, the first file alphabetically, or a top-level component) to write a one-line description of what lives there.

Keep architecture-map descriptions short, concrete, and grep-able. Examples:

- `lib/auth/` — Supabase auth wrappers and session helpers (issue 001b)
- `lib/sync/` — Event sync layer with offline queue (issue 003)
- `components/study/` — Active-session UI primitives (issue 005)

### Step 6. Extract deviations and implementation notes

For each done issue, parse the issue file for two optional sections:

- A heading matching `## Deviations` or `## Deviation` (case-insensitive). Capture content from the heading up to the next `## ` heading or EOF.
- A heading matching `## Implementation notes` or `## Implementation Notes` (case-insensitive). Same capture rule.

Copy the captured content **verbatim** into the per-issue ledger entry — do not summarize, paraphrase, or "improve" it. The user wrote those notes by hand and the exact wording is meaningful.

If a section is absent, write `None recorded` for Deviations. For Implementation notes, omit the line entirely.

### Step 7. Surface open threads

Section 5 should include, in this order:

1. **Drift flags from earlier steps:**
   - Done-by-checkbox issues with zero commits found on `main`.
   - Files listed in commits but missing from `HEAD` (if significant).
   - Issues with no checkboxes at all.
2. **PRD-deferred items:** grep the PRD for sections or lines containing "deferred", "out of scope", "v2", "future", "not in v1". Summarize each as a bullet with the line of context.
3. **Notes flagged as follow-ups:** scan captured deviation/implementation notes for words like "TODO", "follow-up", "revisit", "blocking". Surface each as a bullet citing its issue.

Skip codebase-wide `TODO`/`FIXME` grep — it's noisy and the issue notes already capture the important ones.

### Step 8. Write the output

1. If `CURRENT_STATE.md` exists at the repo root, copy it to `CURRENT_STATE.prev.md` (overwrite any existing `.prev.md` from before).
2. Write the new `CURRENT_STATE.md` using the template above.
3. Report a one-line summary to the user: `"Updated CURRENT_STATE.md. N done, M in progress, K not started. Previous version saved to CURRENT_STATE.prev.md."`
4. If any pause-on-ambiguity items got auto-resolved with a "best guess" rather than a user-asked decision, list them so the user can verify.

## Pause-on-ambiguity rules

These are situations where the skill should stop and ask one targeted question instead of silently picking. Don't batch the questions — handle one, then continue.

- Multiple PRD files match the glob.
- Zero PRD files match the glob.
- Zero issue files match the glob.
- An issue file has no acceptance-criteria checkboxes at all.
- An issue is done by checkboxes but no commits found on `main` after all three tiers.
- Multiple distinct commits match an issue's branch name in the same tier.
- The repo has no `main` branch.
- The repo isn't a git repo at all (skill should run in PRD+issues-only mode and skip sections 2 and parts of 3 — confirm with the user first).

## What this skill deliberately does NOT do

- **Does not preserve hand-edits to `CURRENT_STATE.md`.** The doc is regenerated on every run. Notes belong in the relevant issue file.
- **Does not auto-detect issue completion from git or test results.** Source of truth is checkbox state in the issue file. If checkboxes lie, the doc lies — but consistently, and the drift gets surfaced in section 5.
- **Does not read the entire codebase.** Only files touched by completed issues, plus targeted entry-point sampling for the architecture map.
- **Does not commit the result.** The user commits when they're ready.
- **Does not merge with a previous `CURRENT_STATE.md`.** Full regenerate, every time. Determinism > preservation.
