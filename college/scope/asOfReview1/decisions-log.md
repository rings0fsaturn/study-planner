## Guide feedback that reset the project

At the First Guidance Call the guide directed that **anti-cheating / honest verification**
be a core part of the app: users could pass false session data, so the portal must ingest
study material, track exactly what was studied, and run **periodic assessments** (variety
of quiz types; programmatic for coding, equivalent for theory) generated by an LLM from
the material/transcripts — with attention to LLM cost. The guide also wants a **clear
end-state vision across both phases**. This created **Pillar B**.

## Core scope decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Assessment-based verification is a **co-equal core pillar** (Pillar B), not a peripheral feature | Guide's direct instruction; also fixes the evaluation-validity hole (ground truth for learning) |
| 2 | End-state = **verified closed-loop** adaptive planner; two interlocking pillars (A: adaptation, B: verification) | Pillar B makes the Pillar A loop trustworthy: bad sessions → bad calibration → bad schedule |
| 3 | Phase I = open-loop baseline + **research** assessment options; Phase II = close loop + **build** assessment (the novelty) | Matches PES rubric (Phase II = novelty); preserves novelty; gives authentic unbuilt work |
| 4 | Phase I is **entirely open-loop** (no loop-closing pulled forward) | Protects Phase-II novelty; the app is already open-loop (calibration computed, unused) |
| 5 | Base papers: Pillar A = **Islam 2024** (predict-then-optimize); Pillar B = **CLST 2024** (cold-start KT) | Gives examiners a "build-on-and-improve" story per pillar; novelty = the loop neither does |
| 6 | Base-paper structure = **one primary per pillar** + cited foundations | One base invites "did you reproduce it?"; mirrors the Phase-I/Phase-II objective split |

## Data and evaluation decisions

| # | Decision | Rationale |
|---|---|---|
| 7 | Pillar A data = literature-grounded **synthetic generator** + N=1 real validation | No public dataset has planned-vs-actual pace; controlled ground truth enables precise comparison |
| 8 | Pillar B data = **public KT (Eedi MCQ, POJ coding via pyKT)** + synthetic honest/faker overlay | Real benchmark neutralises "made-up data"; Eedi/POJ match the two assessment modalities |
| 9 | **No real session data yet** → N=1 is validation, not proof; framed honestly at Review 1 | Don't claim validation that doesn't exist; start logging now |
| 10 | Evaluation = **three legs** (synthetic ground truth + public benchmark + closed-vs-open) | Makes single-user data non-load-bearing; this is the open Area-5 answer |
| 11 | Expected outcomes = named metrics + directional hypotheses; only KT-AUC cites a range (~0.70–0.82) | Satisfies "expected outcomes" without over-committing to numbers |

## Technical / architecture decisions

| # | Decision | Rationale |
|---|---|---|
| 12 | KT done at **concept level** with interpretable model (BKT/Deep-IRT) for production; deep pyKT models as offline AUC baselines | Generated/unique items + single-learner break item-level KT; concept-level + cold-start fits; a novelty hook |
| 13 | **Python for research, product runs learned params**; Python is the single source of truth | Evaluated code = shipped code (no TS/Python drift); real libraries (scipy/pyKT) |
| 14 | Single **FastAPI "Intelligence Service" (Docker/Colima)** hosts all heavy ML; consolidates the assessment subsystem | One ML language/service; serves any model; LLM orchestration natural in Python |
| 15 | Pillar A engines migrate **TS → Python** (Phase II); trivial display stays client-side TS for offline | Single source of truth while keeping the log-a-session loop offline |
| 16 | pyKT/pyBKT used as the **model-comparison harness** (offline), not the contribution | Existing models = not novelty; novelty is integration + verified loop |
