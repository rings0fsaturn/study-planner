\chapter{Proposed Methodology}
This chapter describes how the closed loop works and why it takes this shape. Section~4.1 presents the closed learning loop, and Section~4.2 states the candidate models and the selected approach. Section~4.3 describes the comparison methodology. Sections~4.4 and~4.5 trace the design evolution and present the system architecture.

\section{The Closed Learning Loop}
The loop runs over five stages. The learner plans through roadmap-engine bookings and studies through logged sessions. Practice and assessment produce server-graded evidence. Mastery and the loop verdict recalibrate the plan state. The verdict then drives the replan. Figure~\ref{fig:closed-loop} shows the same loop at concept level.

The verdict is advisory and passes a code gate. \texttt{POST /v1/loop/decision} asks the hosted judge for one choice over the week's signals, the evidence summary, and the schedule posture. The code router holds evidence below 0.5 and confidence below 0.7 on \texttt{hold}. Only \texttt{suggest\_replan} carries the verdict pair forward to the replan screen, and the committed \texttt{RoadmapReplanned} mirrors it. \texttt{Keep} writes no event.

Phase~I ran this loop open. It recalibrated pace from logged sessions and raised a prompt, and the learner decided whether to replan. Nothing checked that study produced understanding. Phase~II verifies first: grades steer mastery through Equation~\ref{eq:bkt-update}, mastery and posture steer the verdict, and the verdict steers the plan.

\section{Candidate Models and Selected Approach}
The project fixed each stage by comparing candidates against evidence instead of by default. This section states the candidates and the selected approach per stage. Section~4.3 describes how the comparison ran. Table~\ref{tab:method-candidates} summarizes the selections.

\subsection{Item Generation}
The generator had to produce questions the project can trace. The project rejected multi-family single-call generation without recorded provenance. The selected shape is one family and one question per call, grounded in retrieved chunks with recorded citations. The server gate enforces it: \texttt{formats} must be one of \texttt{objective}, \texttt{written}, or \texttt{coding}, and \texttt{questionCount} must be \texttt{1}. A mixed run alternates families across calls instead of mixing them in one call.

Input is one material, one family, and one scoped chapter. Output is one question with recorded chunk citations, or a terminal warning such as \texttt{code\_not\_derivable} that invents nothing. Format failures drop as \texttt{malformed\_output} after at most one repair. Missing citations drop as \texttt{citation\_missing}. An unverified quote keeps its citation with a \texttt{citation\_unverified} flag.

\subsection{Grading}
One signal cannot judge three families, so each family carries its own authoritative arm. Objective answers are authored at generation time and compared exactly. Written answers go to a rubric-judged model arm. The provider scores each authored criterion, and the module composes the scores with the authored weights at four-decimal precision. The same judgments always give the same score.

An unusable rubric or an empty answer fails closed without retry. A provider payload that does not map onto the rubric returns for redelivery. Code answers execute in the Piston sandbox against hidden tests, and the reference solution never reaches the browser. Every client-side check stays advisory and never enters the grade record.

\subsection{Mastery and Difficulty}
The mastery candidates were the deep and hybrid variants surveyed in Section~2.1. The bake-off held the Bayesian variant at parity with the baseline, so the project kept it and named it bkt-v1. Among the deep and hybrid candidates, the per-skill updater was the simplest at parity. Its estimate is inspectable. The estimate updates per skill through Equation~\ref{eq:bkt-update}.

The shipped parameters are $p_{\text{init}} = 0.15$, $p_{\text{learn}} = 0.1$, $p_{\text{slip}} = 0.05$, $p_{\text{guess}} = 0.2$. Input is the graded response sequence per skill. Output is the mastery probability after each observation with the predicted correctness before it. The TypeScript engine and the Python mirror replay the same golden fixtures with numeric equality to $10^{-6}$. The adaptive chip then maps the estimate to an advisory, uncalibrated difficulty recommendation (see Section~6.1).

\subsection{Guidance and Feedback}
Guidance that gives the answer destroys the evidence the loop reads. The project rejected an open tutor that reveals on demand. The selected shape is the ladder of Nudge, Hint, Targeted explanation, and Reveal, with the last step locked until the learner confirms. The ladder is a state machine: each step streams against retrieved chunks, a request advances one step, and only an explicit confirmation opens Reveal. No transition writes a grade or reaches the grade record.

Feedback copy is also advisory. A server endpoint drafts learner-facing text for updated entries through the \texttt{feedback-v2} template with a static fallback, and the copy never alters the grade.

\subsection{Loop Verdict}
The project weighed a raw model choice against a gated router over it. The project kept the gated pair: the Jev judge (\texttt{jev-1.13} through a hosted API) proposes, and the code router disposes. Input is the week's signals with the evidence summary and the schedule posture. Evidence below 0.5 and confidence below 0.7 land on \texttt{hold}. The gate constant \texttt{LOOP\_APPROVE\_AT} is \texttt{0.7}. Only a confident call with sufficient evidence passes it.

\section{Comparison Methodology}
The comparison rests on two legs. The offline leg scores components against fixed golds. The longitudinal leg scores the whole loop on synthetic histories with known posture. The offline leg informed per-stage selection, and the longitudinal replay validated the assembled loop after the gate fix. The live browser matrix only checks deployment.

The offline leg is the generation-quality harness. It holds golds in \texttt{eval\_golds.json} with three fold hashes at $K=5$, and its gate stays fail-closed by default. It reports groundedness at 0.8667 with a near-duplicate rate of 0.0044. The harness's plain retrieval arm reports recall at 3 of 0.733, and the selected \texttt{hybrid\_rerank} arm reads 0.90 on the 754 split.

On the separate mastery bake-off, bkt-v1 reads 0.888 against 0.889. The live harness reads 0.7397 against 0.7368. Coding derivability on the golds reads 0.0 on the pre-top-up run.

The longitudinal leg replays four synthetic archetypes: steady, crammer, struggling, and returning. The replay tests the planted posture of the four synthetic histories rather than learner behavior. Each run ends in a loop verdict. A \texttt{suggest\_replan} verdict converts when its exact verdict pair joins a \texttt{RoadmapReplanned}. Next-week adherence is reported separately.

The post-fix replay converts 4 of 4 \texttt{suggest\_replan} verdicts into verdict-linked replans over a material-scoped span of 32 days. Verdict confidence reads 1.0, and the judge's evidence-sufficiency score ranges 0.66 to 0.77. Each of the four converted replans selected \texttt{extend-deadline}.

The live matrix confirms deployment. It never promotes a candidate. Objective runs take 2 of 2, and written runs grade 4 of 4 with real rubric grades. Coding runs grade 3 of 3.

\section{System Design and Evolution}
The system reached this shape in three moves. The starting point is the delivered Phase~I design: capacity-based bookings with an open loop. Closed-loop feedback from verified mastery stayed a dashed extension in that design. The base scheduling study~\cite{islam2024} still supplies the predict-then-optimize contrast that design answered.

The second move inserted assessment without touching the booking model. Generation, grading, mastery, guidance, and feedback landed in the intelligence service beside the Phase~I calibration routes. The booking model and session logging did not change, but the local store gained Phase~II attempt and mastery tables. The third move closed the loop through the verdict gate and the verdict pair mirrored onto \texttt{RoadmapReplanned}. The synthetic replay shows that \texttt{suggest\_replan} converted to a verdict-linked replan in all four synthetic histories.

Section~1.2 states the problem, and Sections~3.3 and~3.4 state the requirements.

\section{System Architecture}
The deployed system keeps the Phase~I split. Computation that fits a model to history runs in the Python service. Computation that derives a view from the local event log runs in the client. Supabase sits between them as the data hub with row-level isolation per learner. Figure~\ref{fig:architecture} shows the tiers with the Phase~II additions solid.

The browser client owns bookings, projection, mastery readers, and the verdict handoff. The intelligence service with its worker owns generation, grading, mastery, guidance, feedback, and the loop verdict. The Jev judge runs as a hosted-API client inside the service instead of a separate tier. The GPU inference sidecar serves embeddings and rerank scores from its own compose project, and the sandbox runs learner code on demand. Table~\ref{tab:software} lists the full tier inventory.
