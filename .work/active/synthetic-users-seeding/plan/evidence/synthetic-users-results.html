What we tried to prove, in one sentence each

The report needs three claims a reviewer can audit back to data. Descriptive only - 4 users can never support a significance test, so we never ran one.

The 3 claims
1. Attendance can be measured. Planned study time vs actually logged time, per week.   2. Practice moves knowledge. The app's mastery estimate (called BKT bkt-v1) should rise after real graded practice.   3. The loop closes. When the app suggests a new plan, the learner replans and next week recovers - not just shows advice on screen.

What actually happened

Everything ran through the real app and real servers. Nothing was hand-typed into the database.

  1. 1
    Built the study histories offline

    A small script wrote 20 booked sessions per student across 5 weeks, then kept or skipped each one per that student's attendance pattern. 50 sessions kept in total. Zero grades at this stage - grades can only come from the server.

  2. 2
    Cheap safety check first

    One article, one generated question, one scripted answer. This caught a real bug: the server needs a difficulty 1-5 on every question, which the script was not sending. Fixed before spending more.

  3. 3
    Steady pilot, full cost

    Ingested the 3 shared materials (textbook 422 chunks, talk 167, article 15), appended Steady's history, ran 5 weekly graded runs (12 graded), captured a loop verdict. Fixed a sync gap found here: histories were staying on the device and never reaching the cloud.

  4. 4
    Scaled to the other three

    Same driver, different answer scripts. Crammer 14 graded, struggling 11, returning 6 (3 gap weeks had nothing to grade). Retried every honest failure; 2 of 8 recovered. Cleaned up all junk materials afterwards.

  5. 5
    Extracted report numbers through the real engines only

    Adherence, mastery and verdict tables read through the same roadmap and progress packages the app uses. Every row carries the IDs it came from; a row without a source is rejected by a test.

Honest gaps and bugs found

A seeding run that finds nothing is a seeding run that checked nothing. These are the load-bearing caveats for the report.

Amended target
Original target 160 was unreachable. Locked attendance settings cap sessions at 50, and gap weeks remove runs. Amended with approval: count server grades as observations, N = 113 (50 + 18 + 45). No silent edit.


Missing proof
Closed-loop proof missing. 4 hold verdicts, 0 conversions. Struggling and Returning replans exist but were scripted, not judge-triggered. The extraction pins this honestly instead of masking it.


Found in the run
Bugs the run surfaced: missing difficulty 1-5 on generation calls (fixed test-first) - histories bypassing the sync queue and staying local-only (fixed: route through logEvent, moved seeder inside sync boundary) - loop endpoint needs an Idempotency-Key header (422 without it) - coding self-check fails honestly on hard items (8 terminals, 2 recovered on retry) - EventStore.wipe() clears events but not the queue (left as follow-up, not changed here).
